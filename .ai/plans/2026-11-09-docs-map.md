## Goal

The MVP builds a docs map of a repository besides its C4 model: the Markdown documents as
representations with relations to the code they describe. On Abyme's own repository, the 24
notes of the five folders of `docs/` get elements on boards, related by `describes` to the C4
elements whose code they describe, so that a code change flags the notes that describe it; and
the rule by which later changes keep the model current also covers the notes.

## Context

- The model is built only through the MCP tools `apply` and `verify`, as the C4 model in
  `abyme/` was. The tasks change nothing under an anchor, so each verifies its elements before its
  own commit.
- The notes are those in `docs/1 Vision`, `docs/2 Concepts`, `docs/3 Reconciliation`,
  `docs/4 AI Interface`, and `docs/5 Architecture`.
- The C4 elements a note can describe are those on the boards `context`, `containers`,
  `core-components`, and `canvas-components` (`overview` lists them); the element `abyme` says how
  the model is cut.
- A relation of kind `describes` passes a task to its source: when the code under the target's
  anchor changes, the note is flagged.

notes of its folder as elements, laid out.

### Task 2: Each note describes the code it is about

Each note gets a relation `describes` to the finest C4 element that covers each part of the
existing code the note describes, laid out on its board.

Review path: Reviewer-only

### Task 3: Later changes keep the docs map current

The rule by which changes keep the model current also covers the notes, and the element `abyme`
says how the docs map is cut.

Review path: Reviewer-only

- [ ] An AI agent that adds, removes, renames, moves, or edits a note in the five folders of
      `docs/` learns from the Conventions of the root `CLAUDE.md` what to do with the docs map,
      also when its commit changes no code.
- [ ] A reader of the element `abyme` learns which notes the docs map holds and which it leaves
      out, by the rule and not by a list, and how its relations `describes` are chosen; no
      statement of the element contradicts the docs map, such as that all relations are `uses`,
      that `docs/` is left out, or that the model is C4 only.

## Decisions

- **The 24 notes of the five folders, not the other Markdown files:** `README.md`,
  `Decisions.md`, `Glossary.md`, `Ideas.md`, and `Open Questions.md` at the root of `docs/` describe
  no code, and an element for them would collect relations to everything or to nothing; the
  Markdown outside `docs/`, such as the plans, the READMEs, and `.claude/`, is no documentation of
  the system.
- **One board per folder below a board `docs`:** it mirrors the vault and keeps each board small.
- **Relations `describes` to the finest element that covers what a note describes, never to
  `abyme`:** a container as the target flags the note on every change in its crate, and `abyme`
  is anchored on `Cargo.toml`, so a note related to it would be flagged by almost no code change.
- **No relations between notes:** a `see_also` passes no flag, and the many wikilinks between notes
  would crowd the boards; Obsidian already shows them.
- **Types `docs/note` and `docs/folder`, and every board a zone `mirrored · current`:** the types
  follow the namespaced form of the C4 types, and the notes and their folders exist in the
  repository, which the boards follow as the C4 boards do.
